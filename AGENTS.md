# AGENTS.md

## Project overview

Kelivo is a cross-platform LLM chat client built with Flutter, targeting iOS, Android, macOS, Windows, and Linux. Package name is `Kelivo` — imports use `package:Kelivo/...`.

## Fork workflow

This checkout is a fork of `Chevey339/kelivo`: `origin` points at upstream,
`myfork` at `Dave-12138/kelivo`. Development happens on `for-temp-use`, the
fork's main branch, which is periodically rebased onto `origin/master`. Its
commit hashes therefore change, and rebase conflicts come from changes that
overlap upstream edits, so keep commits small and localized. Do not rebase,
reset, or push `for-temp-use`; the branch owner maintains it.

## No local Flutter toolchain

`flutter` and `dart` are not installed in this environment, so nothing can be
built, tested, formatted, or generated locally: `dart format`, `dart analyze`,
`flutter test`, `flutter pub get`, `flutter gen-l10n`, and
`dart run build_runner build` are all unavailable. There is no `gh` CLI and no
GitHub token either.

Every check and every build runs in GitHub Actions on the fork:

- `pr-check.yml` runs on pull requests targeting `master` and covers the format
  check on changed Dart files, `flutter gen-l10n` with a clean `lib/l10n`
  diff, an untranslated-message check, `dart analyze --fatal-infos`,
  `flutter test`, and the same analyze/test pair for `dependencies/markstream`.
- `build.yml`, `build-stable*.yml`, and `build-linux-arm64.yml` only run
  through manual `workflow_dispatch`. They produce the Android, iOS, macOS,
  Windows, and Linux artifacts and optionally publish a release.

A commit on `for-temp-use` triggers no workflow until a pull request is opened
or a build workflow is dispatched, and an agent can neither push nor read the
run results. Read the code carefully instead, and state what still needs
verification rather than claiming that analysis or tests passed.

## Architecture

- **Feature-based structure**: `lib/features/<feature>/` with `pages/`, `widgets/`, `models/`, `utils/` subdirectories.
- **Desktop / mobile split**: most UI pages have separate desktop and mobile layouts (e.g. `home_desktop_layout.dart` / `home_mobile_layout.dart`). Desktop-only code lives in `lib/desktop/`. Use `ResponsiveHelper` from `lib/shared/responsive/` to branch by screen type.
- **State management**: Provider (`lib/core/providers/`).
- **Database**: Drift (`lib/core/database/`). Schema versions tracked in `drift_schemas/`.
- **Localization**: ARB-based (`lib/l10n/`), English template (`app_en.arb`). The generated `app_localizations*.dart` is committed alongside the ARB files; `flutter gen-l10n` updates both and CI rejects any diff under `lib/l10n`.

## Pre-commit checklist

The commands below need a Flutter/Dart SDK and run in CI or on a machine that
has one, not in this environment. Since `dart format` cannot run here, match the
formatting of the surrounding code by hand; CI runs
`dart format --set-exit-if-changed` on changed files under `lib/`, `test/`,
`integration_test/`, `dependencies/markstream/lib/`, and
`dependencies/markstream/test/`, and fails on any difference. For code changes,
run static analysis before committing:

```bash
dart analyze --fatal-infos lib test integration_test
(cd dependencies/markstream && flutter pub get && dart analyze --fatal-infos)
```

For ordinary changes, run only the test files or directories covering the
changed behavior and affected callers, using `flutter test <test paths>`.
If `markstream` is affected, also run its relevant tests from
`dependencies/markstream`; root-package checks do not cover this path package.

Run the full test suites locally only when merging a major feature, such as a
cross-feature integration or broad architectural change:

```bash
flutter test
(cd dependencies/markstream && flutter pub get && flutter test)
```

All required checks must pass. Documentation-only changes do not require Dart
analysis or Flutter tests. CI (`pr-check.yml`) runs static analysis and the
full test suites for both packages on every pull request targeting `master`.

## Generated output

`pubspec.lock` records a `sha256` for every package and CI installs with
`flutter pub get --enforce-lockfile`, so a dependency change needs a lockfile
regenerated by the Flutter SDK. The same holds for the Drift code and the
`drift_schemas/app_database` export (`dart run build_runner build`) and for
`lib/l10n/app_localizations*.dart`. When a change touches `pubspec.yaml`, Drift
table definitions, or ARB files, hand the regeneration to the user; only
`app_localizations*.dart` is small enough to update by hand from the ARB
source.

## Benchmarks are not tests

`test/perf/*_bench.dart` print timings and contain no `expect()`, so they cannot
fail. They are named out of the default `_test.dart` glob and so are skipped by
`flutter test`. Run one explicitly:

```bash
flutter test test/perf/timeline_scroll_bench.dart
```

## UI guidelines

- **Use app-defined widgets** from `lib/shared/widgets/` and `lib/shared/dialogs/` instead of raw Flutter/Material widgets wherever an equivalent exists (e.g. `SectionCard`, `CustomBottomSheet`, `IosFormTextField`, `IosCheckbox`, `InteractiveDrawer`).
- **BottomSheet**: both Flutter's built-in bottom sheet and `CustomBottomSheet` are fine on mobile. Never use any bottom sheet on desktop — use a dialog or another interaction pattern instead.
- **Icons**: use `lucide_icons_flutter`, not `Icons.*` from Material.
- **Animations**: use `flutter_animate` / `animations` for motion.
- When building a new page, create separate desktop and mobile layouts unless the page is trivially simple. Wire them together via `ResponsiveHelper`.

## Code style

- Do not preserve backward compatibility. Remove obsolete paths instead of adding compatibility layers, fallbacks, or migrations.
- Choose the simplest implementation that fully meets the current requirements. Avoid speculative abstractions, configuration, and indirection.
- Grow the system in layers. Start from the smallest version that works end to end, and add each new capability on top of a product that already works. Never trade a working product for unfinished complexity.
- Keep components modular and concerns clearly separated.
- Prefer established, well-maintained libraries when they reduce overall complexity or improve reliability. Do not reimplement common functionality without a clear reason.
- Lean on the dependencies already in the project before writing your own implementation or adding packages. Do not assume a library lacks a capability without checking its documentation and types.
- Make architectural decisions for the long term. Do not accept a stopgap that only works for now and is meant to be replaced later.

## Local dependencies

Several packages live under `dependencies/` and are referenced by path in `pubspec.yaml` (e.g. `markstream`, `mcp_client`, `flutter_tts`, `flutter_math_fork`, `downsize`). The analyzer excludes `dependencies/flutter_math_fork/**` and `dependencies/flutter_tts/**`.

## Android release signing

`android/app/build.gradle.kts` only attaches a release signing config when
`android/key.properties` exists; otherwise `flutter build apk --release` emits an
unsigned APK. Gradle resolves `storeFile` relative to the `app` module, so
`storeFile=key.jks` means `android/app/key.jks`, while the properties file lives
at `android/key.properties`.

The Android job in every `build*.yml` decodes four repo secrets —
`SIGN_KEYSTORE_BASE64` (base64 of the `.jks`), `KEYSTORE_PASSWORD`, `KEY_ALIAS`,
`KEY_PASSWORD` — and is gated by `if: env.SIGN_KEYSTORE_BASE64 != ''`. The runner
merges a step's own `env:` into the `env` context before evaluating that step's
`if`, so this works; what is *not* allowed in a step `if` is `secrets.*`. Forks
must set the secrets themselves, and environment secrets only reach a job that
declares `environment:`.

## Pinned native dependency workarounds

`dependency_overrides` in `pubspec.yaml` pins native implementations for
compatibility: `sherpa_onnx_*` (macOS deployment target) and
`shared_preferences_android` below 2.5.0 (2.5.0's Pigeon-JNI backend throws
`NoSuchMethodError` on `SharedPreferencesApiRegistrar.getAll` in R8 release
builds, killing Android startup — flutter/flutter#194649). Remove each pin once
the upstream package ships a fix.
